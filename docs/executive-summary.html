How a submission works—only after every gate passes.

1 · Obtain the correct file

Use the downloadable -zeros.tif or the ZIP containing exactly that one TIFF. Do not upload the audit JSON, HTML page, preview PNG, feature raster, or fault catalogue. The current file may be downloaded for research only.

2 · Let the project validate it

Run python generate_submission.py --with-data in the project’s pinned environment. It checks the exact bytes, one-band float32 grid, finite [0,1] range, footprint and catalogue zeros, ZIP contents, recorded holdout arithmetic, canaries, and gate consistency.

Exit success means the negative deliverable is verified. Read ok_to_submit separately: it is false. No eyeballing or discretionary override is part of validation.

3 · Require a separate selector receipt

A future candidate must beat the comparable holdout best with paired evidence, pass the agreed complete registry, and have an assigned lane. A separate selector must verify the current account’s weekly allowance and rule/data-use eligibility against the official submission page. That authenticated state is unavailable here; the previously quoted weekly cap is not re-verified.

4 · Upload only a genuinely cleared candidate

Not this file. For a future candidate whose gates all pass, open DrivenData → New submission, choose its TIFF or single-TIFF ZIP, and paste its recorded short note. The name and note below identify this research negative, not an approved slot.

5 · Preserve the organizer receipt

Record the exact submitted file’s SHA-256, organizer submission identifier, timestamp and score from the submission-page receipt. Only then label that result ORGANIZER-CONFIRMED. A local HOLDOUT-DTI value or an owner website claim is not such a receipt.
