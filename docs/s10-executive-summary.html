1. What the organizer asks for (verified against the organizer's reference code)

  • Output: one single-band GeoTIFF, same CRS, shape and geotransform as the official sample. The organizer notebook takes CRS and transform from labels.tif and writes a single band (reference notebook, cell 19; fetched via the GitHub blob API).
  • Grid used by this repo (from the mirrored sample, sha256 pinned in registry/data_manifest.json): EPSG:32611, 3730 rows × 3292 columns, 100 m, float32, NaN outside the footprint, values in [0, 1].
  • The reference notebook's predictions are sigmoid probabilities and it notes that thresholding "may be advantageous". The organizer's own encoding is therefore continuous, not necessarily binary.
  • ORGANIZER-CONFIRMED (fetched 2026-10-24): the DrivenData problem description says the submission is "a GeoTIFF raster with fault predictions represented as pixel-wise probabilities or confidence scores between 0 and 1", float32, EPSG 32611, 100 m, same bounds as the training data, null or NaN outside the bounds. Source: competition page 967.
  • ORGANIZER-CONFIRMED: the sample is described as one that "predicts total fault absence". The mirrored sample in this repo is not that: its 60,988 ones are exactly the catalogue cells (IR-91-S10-09). Do not use the mirrored sample as a template for anything you upload.
  • Rules (NLR, September 2026, TP-5700-96647): three submissions per week (§3.2); one entry per competitor (§1.1); generative-AI use must be described in the narrative (§3.2). Key dates are not in the rules; they are on the competition site, and the deadline printed earlier in this repo is not verified.

4. How to make a submission (only for a file whose run card says CLEARED)

  1. Open docs/run-card-S10.json (or a later run card). Use a file only if its verdict is promote and its sha256 matches the file on disk: sha256sum <file>.
  2. Re-run the gates: python3 scripts/validate_raster.py <file> data/official/sample_submission.tif --catalogue data/official/existing_faults.tif. Every gate except "parent-diff" must print PASS.
  3. Pick a unique name in the form <lineage>-<lane>-<yyyymmdd>-<sha8>.tif and a note of at most 140 characters, for example S10 basement ridge K60988 ramp; holdout-DTI 0.017 vs null 0.029; NOT for scoring.
  4. On the DrivenData submission page (New submission): choose the File to submit (single-band GeoTIFF, or a zip containing one), and fill Note (optional) with the short comment from step 3.
  5. Record the organizer receipt (score and date) in ledger/submissions.csv under receipt_score and receipt_date only. Never put a model projection there.
  6. The weekly cap (three per week, rules §3.2) and the deadline on the DrivenData site are the authority. The deadline printed earlier in this repo is not verified.
If the file rejects with "Predicted values must be in range [0, 1]":

Likely causes, to check in this order (inferred, not confirmed against the organizer validator): (a) a nodata sentinel such as −3.4e38 written as a value; (b) values above 1 or below 0 written outside the footprint; (c) a zeros-filled raster where the sample is NaN outside. The validator above reports min and max over every finite cell, so run it before uploading.
