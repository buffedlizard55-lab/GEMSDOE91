## 1. Direct answers

### Q1. Why did GEMSDOE32 (`h33-h33-2-b2-…-zeros`, user-reported 0.2778) score highest, and can we beat it?

**Evidence status.** The 0.2778 figure is a user report. No organizer receipt exists in the repo, and the DrivenData leaderboard page does not show it (see §2). Repo forensics ([`docs/s16/gems32-forensics.json`](s16/gems32-forensics.json)) establish only geometry:

* The 37,654-dot file is exactly a 40,199-dot base with **2,545 dots within 200 m of the USGS catalogue removed**, and no dots added (`r0_added_vs_base = 0`).
* Median nearest-neighbour spacing is **3 px**.
* The advertised ZIP contains a **0-byte member**, not a TIF (`single_nonempty_tif = false`).

**Mechanism (reasoned from the official metric; not measured).** The official metric (DrivenData page 967) is a distance-weighted Tversky index with α = 0.2 (false positives cheap), β = 0.8 (false negatives expensive), and triangular kernel R = 300 m. Under the organizer's own description, the private test set is *new* faults that are *not* in the USGS database. A dot sitting on a catalogued fault therefore pays false-positive weight unless a new fault happens to lie within 300 m of it. Removing catalogue-adjacent dots lowers unmatched mass `S−M` while keeping most truth coverage `T`, so DTI rises. The README's closed form, `DTI = T/[0.2T + 0.2(S−M) + 0.8|G|]`, follows from the official definitions once `FN_w = |G| − TP_w`, and `tests/test_dti_official_formula.py` checks it against a brute-force transcription of the official formula.

The marginal rule that follows: adding a dot with expected truth gain ΔT and unmatched mass ΔF raises DTI only if

> ΔT / ΔF > 0.2·T / (0.2·F + 0.8·|G|),  with F = S − M.

This is a plausible explanation, not causal proof. The repo cannot separate a hidden-score effect from geometry alone.

**Could we beat the UNVERIFIED user-reported 0.2778?** Not demonstrated. What we can say:

* **Our own holdout is measuring the wrong thing for this competition.** It withholds *catalogue* faults and rewards recovery of them, while the official private set is *new* faults. The repo's own off-catalogue control shows the gap. For example, `S14-HVDC E2` scores **HOLDOUT-DTI 0.262209** (`SLOT_PLAN.md`), while the blind SGMC off-catalogue control scores **0.110429** (`SLOT_PLAN.md`; a control score, neither HOLDOUT-DTI nor ORGANIZER-CONFIRMED). The control is closer to the competition target, although its provenance is currently unverified (IR-91-S18-06).
* **The holdout cannot judge the 0.2778 mechanism at all.** The repo already built collar-pruned variants of GEMSDOE32's file (PRUNE le4, le5 and le10, delete-only, 2026-10-23; [variant card](../ledger/variant-cards-PRUNE-20261023.md), [evidence](../evidence/prune_ladder_20261023.json)). The card reports that the holdout proxy is **0.0 for all three**, because once every dot within 3 px of the catalogue is removed, no remaining dot can touch a withheld catalogue cell. The instrument is blind to the very effect in question. Only an off-catalogue control can test it, and the control's provenance is not yet verified (IR-91-S18-06).
* Holdout numbers from different evaluator versions (`gems57-pooled-hide-v2` and `gems91-hide-recover-v1.0`) are not directly comparable.
* No file in the repo has an organizer score receipt. The user-reported 0.2778 is UNVERIFIED, so no comparison to it or to any leaderboard score is verified.

## 3. Uniqueness gate: why no competitive file can pass it

**Two different rules are in play.**

* **Team protocol** (user's Parallel-Run Protocol, rule 1): rank correlation > 0.90, or more than 70% of dots within 3 px of **one** registry raster's dots → duplicate stop.
* **Official rules**: no such rule (S8).

So the 70% gate is an internal policy. It is binding on the team, but the competition does not impose it.

**Geometry under the team gate.** The frozen registry lattice `calib_r13lattice_00904.tif` (the public submission `20261001_r13-lattice-s5_v2_nan-outside`, 0.0904, on the user's list) covers **99.871%** of the 5,167,373-pixel footprint within 3 px. Only **6,649** pixels are uncovered ([`docs/s16/registry-feasibility.json`](s16/registry-feasibility.json)).

* At N = 37,654 dots, overlap ≥ (N − 6,649)/N = **82.34%** > 70%. Infeasible. Reproduced by `verify_s18.py`.
* The bound depends on dot count. The threshold can be met only if N ≤ U/0.30 = **22,163** dots, and then **at least 30% of the dots must sit on the 6,649 uncovered pixels**. That placement is chosen to avoid a registry file, not to detect faults. It is the "anti-registry noise" the repo refused in S16, and I did not implement it.

**Consequence.** Any dense candidate placed on fault-plausible ground overlaps the lattice at about 100%. Under the team's own rule, the only file that passes is one shaped by the registry rather than by geology. That is the decision the user has to make (§6, D1).

## 5. Candidate hypotheses (3–5), ranked — none validated, none implemented

Ranking uses expected DTI improvement × implementation cost, with preference for data already in hand. "Grep" means I searched `docs/HYPOTHESES_*.md`, `docs/MECHANISM*.md`, `docs/GEOTHERMAL_VENT_KNOWLEDGE_BASE.md`, `scripts/` and `src/` on this branch.

**H1 (top) — Topographic roughness / Hurst-exponent break across lineaments.**
* *Layer:* detrended elevation (`det_elev`, already a training-feature band) at 100 m; the 1-m DEM from the competition's DEM link list is the higher-resolution option.
* *Signature:* a step change in local spectral slope (Hurst exponent) of the detrended surface across a lineament. Fault-zone fracturing and erosion change the texture of the surface.
* *Why it should catch missing faults:* concealed or unmapped scarps under thin alluvium have little relief but can still change texture.
* *Non-fault mimic:* lithologic contacts (hard vs soft rock), alluvial-fan and playa margins.
* *Difference from repo:* grep finds **no** Hurst-exponent or fractal-roughness implementation. "Roughness" appears in 2 files (magnetic and BHAR contexts) with no spectral or fractal method implemented. "Hurst" hits are substrings of "Thurston" (Thurston–Smith SPI), not the method. The existing RELIEF and SNAP axes use terciles and gradients, not spectral slope.
* *Cost:* low on CPU. The 100 m version uses restricted training features (already restored). The 1-m version needs DEM tiles that this sandbox cannot download.

**H5 — Score the existing PRUNE variants on an officially sourced off-catalogue control (measurement, not a submission).**
* *Layer:* PRUNE le4/le5/le10 files already built from GEMSDOE32 R0 (2026-10-23); the SGMC off-catalogue fault raster after re-derivation from an official SGMC release (S13).
* *Purpose:* answer "why is the UNVERIFIED user-reported 0.2778 high" with the one instrument that can see the collar effect. Each PRUNE variant changes mass and geometry together, so the result attributes the gain only to the collar in combination with mass loss (the variant card says so explicitly).
* *Value:* it shows whether removing catalogue-adjacent dots raises off-catalogue credit or only lowers the denominator.
* *Cost:* low once the control is re-derived. It needs the official SGMC download, which is blocked in this sandbox (IR-91-S18-10), and it needs the control's provenance fixed first (IR-91-S18-06).
* *Difference from repo:* the PRUNE ladder exists, but its variants were never scored on an off-catalogue control, because the catalogue holdout is blind to them (see §1).

**H4 — Calibrated continuous emission rather than binary dots.**
* *Rationale:* the official metric accepts probabilities p ∈ [0, 1]. Binary dots are a special case. Scaling every p by a constant c multiplies TP_w and FP_w by c but raises FN_w, so the optimal emission is not simply binary or uniform; it depends on the calibration.
* *Difference from repo:* every candidate file on this branch is a binary dot set. The soft-probability penalty is analysed conceptually in `docs/HYPOTHESES_SPID91.md`, but I found no same-model binary-vs-continuous comparison under the official metric in `evidence/`. **To verify before relying on this.**
* *Cost:* low (one re-emission per existing posterior).

**H2 — Landsat C2 L2 surface-temperature residuals along lineaments.**
* *Layer:* USGS Landsat Collection 2 Level-2 surface temperature (S14: official, free).
* *Signature:* linear thermal residual against the regional trend, especially at night in winter, from shallow advective heat along fault-controlled upflow.
* *Mimics:* irrigation, evaporation and playa salinity, albedo and aspect, urban heat.
* *Difference from repo:* grep for "Landsat" returns 0 hits.
* *Cost:* high. Multi-scene download and processing. **Blocked in this sandbox**, which allows only github, npm and pypi. This needs an unrestricted machine.

**H3 — NWIS groundwater-level discontinuities as hydraulic baffles.**
* *Layer:* USGS water-level records via the successor API (S15). The legacy Water Services API is being shut down on 2027-02-22.
* *Mimic:* pumping and irrigation drawdown.
* *Overlap risk:* the S15 aquifer-baffle lane uses the same physical idea (`docs/HYPOTHESES_S15_SCGF.md`). Its well data source is not NWIS, but the mechanism is the same, so this is likely a duplicate lane. Ranked last for that reason.

**Recommended order:** H1 first (best expected gain per unit cost, new signal). H5 second (it is the only test that can answer the question about the UNVERIFIED 0.2778 claim, but it is blocked until the control is re-derived). H4 third (cheap, but needs the check noted above). H2 and H3 are data-blocked or overlap-limited.

**Budget.** The protocol allows 3 experiments or 2 hours. This session used 0 experiments. Validate H1 first on the shared holdout. If it does not beat the current comparable holdout best, record it as a negative and stop.

* **IR-91-S18-10 — Sandbox egress.** Only github, npm and pypi are reachable for bulk downloads. USGS, Landsat, NWIS and DrivenData bulk data need an unrestricted machine.
* **IR-91-S18-11 — AI-use disclosure.** Rules §3.2 require disclosure of generative-AI use in the narrative. The repo has `AI_USE.md`; it must be included in any submission narrative.
* **IR-91-S18-12 — Holdout structurally blind to the collar mechanism.** The PRUNE variant card records a proxy of 0.0 for every collar variant (see §1).
